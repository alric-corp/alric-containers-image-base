O consumo de Image Base é uma linha `FROM` no Dockerfile da aplicação. A imagem final é construída pela esteira da sua squad, publicada no registry da aplicação e implantada no Amazon EKS ou no Amazon ECS.

## Referência da imagem {#referencia-da-imagem}

```text
758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-<framework>:stable
```

- **`<framework>`** é o nome da imagem no [catálogo](../catalogo/index.md), como `java21`, `go1-26-dev` ou `python3-13`.
- **`758421218117.dkr.ecr.sa-east-1.amazonaws.com`** é o registry corporativo de Image Base (Amazon ECR, região `sa-east-1`). O `FROM` aponta direto para ele.
- O acesso ao registry de Image Base é feito pela esteira: você não precisa de credenciais nem de `docker pull` local. Se a sua esteira ainda não consome Image Base, solicite a habilitação pelo [canal de suporte](../suporte.md).
- Não coloque credenciais no Dockerfile e não crie tags nos repositórios `image-base-*`.

## Artefato pronto: somente runtime {#artefato-pronto}

Quando a esteira já compila a aplicação, o Dockerfile apenas copia o resultado para o runtime.

<Tabs groupId="linguagem" queryString>
<TabItem value="go" label="Go">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-go1-26:stable
COPY --chown=10000:10000 servidor /app/servidor
ENTRYPOINT ["/app/servidor"]
```

O binário precisa ser estático (`CGO_ENABLED=0`) e compilado para a arquitetura de destino.

</TabItem>
<TabItem value="java" label="Java">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-java21:stable
COPY --chown=10000:10000 target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

O JAR precisa ter sido compilado para a versão do Java da imagem ou anterior.

</TabItem>
<TabItem value="dotnet" label=".NET">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-dotnet10:stable
COPY --chown=10000:10000 publish/ /app/
ENTRYPOINT ["dotnet", "/app/MinhaApp.dll"]
```

Publique para o .NET 10 sem runtime embutido: `dotnet publish -c Release --no-self-contained`.

</TabItem>
<TabItem value="node" label="Node.js">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-nodejs24:stable
COPY --chown=10000:10000 dist/ /app/
ENTRYPOINT ["/usr/bin/node", "/app/server.js"]
```

Se o bundle não inclui as dependências, copie também o `node_modules` de produção, preparado para a mesma arquitetura.

</TabItem>
<TabItem value="python" label="Python">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-python3-13:stable
COPY --chown=10000:10000 deps/ /app/deps/
COPY --chown=10000:10000 src/ /app/
ENV PYTHONPATH=/app/deps
ENTRYPOINT ["/usr/bin/python3", "-B", "/app/app.py"]
```

A esteira prepara `deps/` com `pip install --target deps -r requirements.txt`, usando o Python 3.13 e a arquitetura da imagem de destino. Extensões nativas precisam de wheels para Linux com glibc nessa arquitetura.

</TabItem>
</Tabs>

## Build multi-stage com `-dev` {#multi-stage}

Use quando a compilação ou a instalação de dependências acontece dentro do Docker: a `-dev` no estágio de build e o runtime da **mesma família e versão** no estágio final. Os exemplos seguem o padrão das aplicações de referência que a plataforma constrói e executa nas duas arquiteturas antes de cada promoção.

<Tabs groupId="linguagem" queryString>
<TabItem value="go" label="Go">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-go1-26-dev:stable AS build
ENV HOME=/tmp CGO_ENABLED=0
WORKDIR /app
COPY --chown=10000:10000 . .
RUN go build -trimpath -o /app/servidor .

FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-go1-26:stable
COPY --from=build --chown=10000:10000 /app/servidor /app/servidor
ENTRYPOINT ["/app/servidor"]
```

Os módulos vêm do `GOPROXY` configurado na esteira, que deve apontar para a fonte corporativa autorizada.

</TabItem>
<TabItem value="java" label="Java">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-java21-dev:stable AS build
ENV HOME=/tmp
WORKDIR /app
COPY --chown=10000:10000 . .
RUN ./mvnw -B package

FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-java21:stable
COPY --from=build --chown=10000:10000 /app/target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

A `-dev` traz o shell que os wrappers `mvnw` e `gradlew` exigem. Com Gradle, use `./gradlew build` e copie o JAR de `build/libs/`. Ajuste o nome do JAR ao seu projeto.

</TabItem>
<TabItem value="dotnet" label=".NET">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-dotnet10-dev:stable AS build
ENV HOME=/tmp DOTNET_CLI_HOME=/tmp NUGET_PACKAGES=/tmp/nuget \
    DOTNET_CLI_TELEMETRY_OPTOUT=1 DOTNET_NOLOGO=1
WORKDIR /app
COPY --chown=10000:10000 . .
RUN dotnet publish -c Release -o /app/out --no-self-contained

FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-dotnet10:stable
COPY --from=build --chown=10000:10000 /app/out /app/out
ENTRYPOINT ["dotnet", "/app/out/MinhaApp.dll"]
```

O `dotnet publish` também restaura os pacotes, usando o `NuGet.config` do contexto quando o projeto define a fonte corporativa autorizada. Exclua `bin/` e `obj/` no `.dockerignore`.

</TabItem>
<TabItem value="node" label="Node.js">

```dockerfile title="Dockerfile"
FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-nodejs24-dev:stable AS build
ENV HOME=/tmp npm_config_cache=/tmp/npm-cache
WORKDIR /app
COPY --chown=10000:10000 package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=10000:10000 . .

FROM 758421218117.dkr.ecr.sa-east-1.amazonaws.com/image-base-nodejs24:stable
COPY --from=build --chown=10000:10000 /app /app
ENTRYPOINT ["/usr/bin/node", "/app/server.js"]
```

Se o projeto tem etapa de build (TypeScript ou bundler), rode `npm ci` e `npm run build` no estágio `-dev` e copie para o runtime somente a saída e as dependências de produção.

</TabItem>
<TabItem value="python" label="Python">

Python não tem variante `-dev`. Prepare as dependências fora da imagem e use o exemplo de [artefato pronto](#artefato-pronto).

</TabItem>
</Tabs>

## Boas práticas {#boas-praticas}

- **`ENTRYPOINT` e `CMD` em formato de lista**, como `["java", "-jar", "/app/app.jar"]`. O runtime não tem shell, então o formato de texto (`CMD java -jar app.jar`) falha.
- **`COPY --chown=10000:10000`** mantém os arquivos com o usuário da base. Não troque para `USER root`.
- **Nada de `RUN` no estágio final**: o runtime não tem shell nem gerenciador de pacotes. Instalações e compilações ficam no estágio `-dev`.
- **Gravação em disco**: com raiz somente leitura, a aplicação grava apenas em diretórios montados, como `/tmp`. Nos estágios de build, `ENV HOME=/tmp` direciona os caches das ferramentas para um diretório gravável.
- **`.dockerignore`** deve excluir `.git`, `.env`, credenciais e caches (como `bin/`, `obj/` e `node_modules/` do host), sem excluir o que o Dockerfile copia.
- **Dependências** de Maven, Gradle, npm, NuGet, pip e módulos Go vêm das fontes corporativas autorizadas.
- **Tokens** de registries de dependências entram pelo mecanismo de secrets da esteira ou do BuildKit, nunca por `ARG`, `ENV` ou URL com senha. Veja [build secrets](https://docs.docker.com/build/building/secrets/).

## Reconstruir após atualizações da base {#reconstruir}

Uma nova versão da base só chega à aplicação quando ela é reconstruída com a base atualizada, testada e implantada. O build precisa consultar a versão atual da tag `stable` (`docker build --pull` ou o equivalente da esteira); `--no-cache` não substitui `--pull`. Detalhes em [Atualizações e CVEs](../seguranca/atualizacoes.md).

## A imagem final é da squad {#imagem-final}

Scan, assinatura, SBOM e deploy da imagem final seguem na esteira da squad. A assinatura da base não assina a imagem derivada, e o SBOM da base não lista as bibliotecas que a aplicação acrescenta.
